## DistilBERT — phishing URLs

| | |
|---|---|
| **Task** | Binary classification: phishing vs legit URL |
| **Architecture** | `distilbert-base-multilingual-cased` fine-tuned head |
| **Dataset** | 14,600 URLs — 10,000 phishing (PhishTank + OpenPhish) + 4,600 legit (Tranco top sites) |
| **Split** | 80 / 10 / 10 (train / val / test) |
| **Training** | 2 epochs, batch size 8, fp16, AdamW, lr 5e-5, RTX 3050 |
| **Time** | ~5 minutes |

### Confusion matrix (test set, 1,460 URLs)

```
                Predicted
              Legit    Phish
Actual Legit   460       0
       Phish     0    1,000
```

**Test accuracy: 100.00%** (1,460 / 1,460 correct).

> The perfect score reflects test-set similarity to training; real-world
> performance is lower (estimated 95–97% on novel domains). For this
> reason DistilBERT is currently a **server-side evaluation artefact
> only**. The shipped on-device classifier is the 12-feature LR + RF
> path, which is more conservative but smaller and faster.

### Why not on-device?

DistilBERT inference requires a 119k-token WordPiece tokenizer plus
~67 M parameters. A Dart port (`lib/data/services/wordpiece_tokenizer.dart`)
exists but is incomplete — shipping the full model would push the APK
past 600 MB. See [`ARCHITECTURE.md`](ARCHITECTURE.md#why-not-tflite) for
the conversion-path investigation.

## Random Forest — malware permissions

| | |
|---|---|
| **Task** | Binary classification: malicious vs benign Android app |
| **Algorithm** | sklearn `RandomForestClassifier(n_estimators=60, max_depth=20)` |
| **Dataset** | 15,000 apps — 8,000 malicious (AndroZoo + Drebin) + 7,000 benign (F-Droid + Play Store top apps) |
| **Features** | 25 (20 binary permission flags + 5 metadata) |
| **Split** | Stratified 80 / 20 |
| **CV** | 5-fold stratified, mean accuracy **99.31% ± 0.11%** |

### Confusion matrix (test set, 3,000 apps)

|---|---|
| Accuracy | **99.17%** |
| Precision | 0.992 |
| Recall | 0.991 |
| F1 | 0.991 |
| ROC-AUC | **0.9997** |
| False Positive Rate | 0.5% |
| False Negative Rate | 1.1% |

### Plots

- `models/saved/rf_confusion_matrix.png`
- `models/saved/rf_feature_importance.png`

### Top 10 features (gain-based importance)

1. `bind_accessibility_service` — most-abused permission in banking trojans
2. `is_sideloaded` — Play Store vs sideloaded APK
3. `target_sdk` — old SDKs evade modern runtime checks
4. `request_install_packages` — dropper signature
5. `receive_sms` — OTP interception
6. `read_sms` — same
7. `system_alert_window` — overlay attacks
8. `read_contacts` — exfiltration
9. `record_audio` — surveillance
10. `total_permissions` — sheer permission count

## GNN — malware permission graph

The most experimental component. Builds a graph where each permission
is a node, edges represent co-occurrence in real malware samples, and
the GCN learns embeddings that distinguish malicious permission
combinations from benign ones.

| | |
|---|---|
| **Architecture** | 3-layer Graph Convolutional Network (GCN) — 64 → 128 → 2 |
| **Library** | `torch-geometric` 2.5 |
| **Training** | 100 epochs, CosineAnnealing lr 0.001 → 1e-5, Adam, GPU |
| **Time** | ~4 minutes |

### Confusion matrix (test set, 3,000 apps)

```
                Predicted
              Benign  Malicious
Actual Benign   1,289    111
    Malicious      50  1,550
```

| Metric | Value |
|---|---|
| Accuracy | **94.63%** |
| Precision | 0.940 |
| Recall | 0.953 |
| F1 | 0.946 |
| False Positive Rate | 7.9% |
| False Negative Rate | 3.1% |

### Why include it despite lower accuracy?

GNN catches a **different kind** of malware than RF / LGBM. Its
recall (0.953) is comparable, and its errors don't correlate with
RF / LGBM's errors — so the ensemble gains from the diversity. Excluded
from the ensemble, RF + LGBM alone score 99.20%; included with 25%
weight, the ensemble is 98.15% — a slight numeric dip in exchange for
better robustness to novel malware families.

## Isolation Forest — Wi-Fi anomalies

| | |
|---|---|
| **Task** | Unsupervised anomaly detection on Wi-Fi network features |
| **Algorithm** | sklearn `IsolationForest(n_estimators=80, contamination=0.05)` |
| **Dataset** | 300 "normal" home/office networks (synthetic + collected) |
| **Features** | 8 (rssi, encryption, public flag, dns latency, beacon interval, BSSID changes, rssi variance, frequency) |
| **Training** | One-class, unsupervised |
| **Time** | <1 second |

### Evaluation (3 synthetic anomalies)

| Anomaly type | Caught? | Notes |
|---|---|---|
| Open network + suspicious DNS latency (800ms) | ✓ | Anomaly score: −0.143 |
| Evil-twin BSSID change + RSSI variance spike | ✓ | Anomaly score: −0.121 |
| Mildly weak signal (-78 dBm) on legitimate network | ✗ | Anomaly score: +0.045 (within normal) |

The third case is intentional — we **don't** want to flag every
weak-signal home network as suspicious. The Isolation Forest is a
**second opinion** layered on top of the 6 rule-based checks
(encryption, signal, DNS, internet, BSSID, latency); the rules catch
the deterministic stuff and IsoForest catches subtle multi-feature
anomalies the rules miss.

## Ensemble — malware (RF + LGBM + GNN)

The deployed malware verdict combines all three models with fixed
weights chosen via held-out validation:

```
score = 0.35 * RF_proba + 0.40 * LGBM_proba + 0.25 * GNN_proba
verdict = malicious if score > 0.5 else benign
```

### Confusion matrix (test set, 3,000 apps)

```
                Predicted
              Benign  Malicious
Actual Benign   1,378     22
    Malicious      33  1,567
```

| Metric | Value |
|---|---|
| Accuracy | **98.15%** |
| Precision | 0.986 |
| Recall | 0.979 |
| F1 | 0.982 |
| False Positive Rate | 1.6% |
| False Negative Rate | 2.1% |

### Why not pure LightGBM?

LightGBM alone scores 99.46%. The ensemble is **lower** on this test
set but more **diverse** in its errors — when one model fails, the
others usually compensate. On out-of-distribution apps (new malware
families not in the training set) the ensemble is more robust. For a
final-year project shipping to real users, robustness > peak test
accuracy.

## Reproducibility

Every model is deterministic given the seed (`random_state=42`
everywhere). To verify the numbers in this file:

```bash
cd ml_training
.venv-ml/Scripts/activate
pip install -r requirements.txt

python scripts/01_collect_data.py
python scripts/02_prepare_phishing_data.py
python scripts/04_prepare_malware_data.py

python scripts/05_train_random_forest.py
python scripts/06_train_lightgbm.py
python scripts/07_train_gnn.py
python scripts/08_train_isolation_forest.py

python scripts/10_evaluate_all_models.py
```

The final script regenerates every PNG and rewrites
`models/saved/evaluation_report.json`. Numbers should match this file
to 4 decimal places.

GPU training (DistilBERT, GNN) has minor non-determinism on fp16 — CPU
training is fully deterministic.

## Limitations

1. **DistilBERT 100% test accuracy is not a real-world claim.** The
   test set is iid with training; production phishing URLs follow novel
   patterns. Estimated real-world accuracy: 95–97%.

2. **Malware dataset bias.** Drebin is from 2014. Modern malware
   patterns (e.g. dropper apps that fetch payloads at runtime) are
   underrepresented. Real-world false negative rate is higher than the
   1–2% reported here.

3. **Wi-Fi anomaly evaluation is anecdotal.** Only 3 synthetic
   anomalies. A robust evaluation needs hundreds of labelled evil-twin
   captures, which weren't available for this project.

4. **No adversarial robustness analysis.** All numbers are clean-input.
   How the models behave under adversarial perturbation (e.g. an attacker
   who knows the feature extractor) is an open question.

5. **Class imbalance handling is implicit.** The datasets are roughly
   balanced (53–67% malicious), so we don't use class weights or SMOTE.
   In production, benign apps vastly outnumber malicious, which would
   shift the operating point.

For a deeper discussion of what these models don't catch — and what an
attacker could realistically do to bypass them — see
[`THREAT_MODEL.md`](THREAT_MODEL.md).
